# VM 侧项目亮点 —— SmolVLA 六轴机械臂控制 POC

> 用途：**简历提炼**（项目篇幅约 **3~5 行**）。
> 细节见 [`problems.md`](problems.md)；项目构成 = **7 包 / 5 节点**（ROS2 Jazzy）。

---

## 1. 一句话定位

把幻尔 STM32 六轴机械臂控制栈移植为 ROS2 分层架构（驱动 / 语义网关 / 应用），
打通「**Windows 宿主机（不装 ROS2）↔ VM ↔ 舵机总线**」的**实测角采集 + 动作回放**闭环，服务于 LeRobot / SmolVLA 数据链路。

---

## 2. 简历版（VM 侧，最多 2~3 行）

### 3 行版（推荐）

> **SmolVLA 六轴机械臂控制 POC** ｜ ROS2 Jazzy / Python / 串口协议 / TCP-JSON
> - 将幻尔 STM32 六轴机械臂控制栈**移植并重构为 ROS2 三层架构（7 包 5 节点，驱动/语义网关/应用）**，打通 Windows 宿主机（**不装 ROS2**）↔ VM ↔ 舵机的实测角采集与动作回放闭环，并扩展出**虚拟串口 ASCII、UDP-VOFA+ 两条额外控制入口**。
> - **定位并修复厂商 SDK 无超时阻塞读 + 持锁导致的状态服务永久死锁**（回放随机卡死、数据流只增不减地断流）；用**阶梯负载实验证伪"总线负载"假设**、锁定运动电流尖峰触发丢响应，把"永久瘫痪"降为 0.3s 抖动；**设计覆盖式（最新帧）数据面解耦生产/消费频率**，慢客户端 4 秒不读时采样仍稳 **20Hz**。
> - **量化串口边界（6 舵机 35ms ≈ 28Hz 上限）并使软限与舵机硬限 100% 对齐**，补齐看门狗失效安全与告警可观测性，下行回放 **22.7Hz** 真机验证通过。

### 2 行版（极限压缩）

> **SmolVLA 六轴机械臂控制 POC** ｜ ROS2 Jazzy / Python / 串口协议 / TCP-JSON
> - 将幻尔 STM32 六轴机械臂控制栈**移植重构为 ROS2 三层架构（7 包 5 节点）**，打通 Windows 宿主机（**不装 ROS2**）↔ VM ↔ 舵机的实测角采集与动作回放闭环，并扩展串口 ASCII / UDP-VOFA+ 两条控制入口；**定位并修复厂商 SDK 无超时阻塞读持锁导致的状态服务永久死锁**（回放随机卡死），以阶梯负载实验证伪总线负载假设后锁定运动电流尖峰，把"永久瘫痪"降为 0.3s 抖动。
> - **设计覆盖式最新帧数据面**解耦生产/消费频率（慢客户端不读时采样仍稳 **20Hz**）；**量化串口边界**（6 舵机 **35ms ≈ 28Hz**）并使**软限与舵机硬限 100% 对齐**，下行回放 **22.7Hz** 真机验证通过。

## 3. 亮点分级（按简历价值排序）

### ★★★ 必写（差异化、有深度）

| 亮点 | 为什么值钱 | 支撑数字/证据 |
|---|---|---|
| **多机/多层系统的端到端打通** | 跨 OS（Windows↔Linux）、跨语言、跨传输（串口二进制帧 / TCP-JSON / UDP-ASCII），且**宿主机不装 ROS2** 仍能闭环 | 7 包 5 节点、3 条控制入口 |
| **厂商 SDK 永久死锁根因定位** | 典型"隐蔽的阻塞式缺陷"：`queue.get(block=True)` 无超时 + 持锁 → 一处丢包瘫痪整条链路。排查用**证伪法**而非猜测 | 断流 2s→7s→12s 只增不减；修复后 **0.10s** 恢复 |
| **实验设计能力：阶梯负载实验** | 主动构造对照实验**推翻自己的假设**（总线负载），再锁定真因（运动电流尖峰） | 20/40/**77Hz** 写入 → **0** 读超时 |
| **覆盖式数据面解耦频率** | 抓住 TCP"发送端无丢弃语义"这一本质，把丢弃放到消费侧，消除"慢客户端拖垮全链路" | 客户端 4s 不读，采样稳 **20Hz**（原 10.7Hz） |

### ★★ 值得写（体现工程规范）

| 亮点 | 说明 |
|---|---|
| **失效安全设计** | 看门狗（命令静默/断连 → SAFE + 卸力）、录制默认下行关闭（**零干扰**）、上力命令连发两次防丢帧 |
| **可观测性建设** | 把沉默失败变成明确告警：`driver NOT ready`、`cannot bind ... another dataset_stream is running`、`bus_servo read timeout`、`no measured frames for Ns: <原因>` |
| **硬件事实量化** | 实测串口带宽（1 舵机 6.4ms / 6 舵机 35ms）→ 反推采样率上限 **28Hz**，据此定参数（建议 20~25Hz） |
| **组件化 / 可测性** | 纯逻辑抽离（`downlink.py` 无 ROS/socket 依赖）→ 可独立单测；下行集成测试 **27 项断言全过** |
| **跨平台兼容治理** | Python 3.10→3.12；厂商 aarch64 IK 库不可用 → 明确设计边界（只做关节/脉宽） |

### ★ 可选（细节，篇幅不够时舍）

- 两个同型号 CH340 **无唯一序列号** → 改用 `/dev/serial/by-path/` 区分物理口
- VMware USB 透传下 CH340 掉线（`Errno 5 EIO`）→ 打开串口**自动重试 30×1s** 自愈
- rclpy `Node` **内部属性重名**导致节点崩溃（`_clients` → `_tcp_clients`）
- 启动时序竞争导致卸力丢包 → 等 `init_finish` 服务就绪
- 残留进程占端口 → 裸 traceback 改友好报错 + 清理脚本（并规避 `pkill -f` 自杀陷阱）
- 自行引入的 regression（`_pending` 守卫把可恢复降级变硬卡死）→ 加 3s 兜底并复盘
